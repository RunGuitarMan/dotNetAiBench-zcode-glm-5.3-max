# Motiva — Stage 3. План разработки и проверок

Статус: r2 — вторая правка по результатам повторной проверки (G3 не пройден; исправления, закрытые в r1, сохранены), ожидает утверждения. Объём стадии — декомпозиция утверждённого решения на исполнимые проверяемые задачи; код приложения не пишется, архитектура не перепроектируется. После утверждения — исполнение. Реализация не начиналась; runtime-проверок на этом шаге нет.
Входы (весь согласованный набор): `docs/01_BUSINESS.md` v3.0 (B01–B37, E01–E12), `docs/02_ENGINEERING.md` v3.0 (T01–T10), `docs/03_AUTH.md` + `auth/jwt.py`, `docs/stage-1.md` (реестр B, SCN-01–07, EDGE-01–05), `docs/stage-2.md` R2 (§1–§8, H0 Q01–Q09, EXTERNALLY_NORMALIZED), `docs/openapi.yaml` 1.2.0 (44 маршрута / 70 методов), `.editorconfig`.

Принципы декомпозиции: задача = проверяемый инкремент со своей проверкой готовности; тесты всех требуемых слоёв (T08) сдаются внутри задачи, интеграционные не копятся в конец; ссылка на утверждённые таблицы предпочтительнее дублирования; оценок в часах нет; детализация — функциональный срез, не строка кода. Ссылки вида §3.0/§3.1/… — на `stage-2.md`; SCN/EDGE/E — на `stage-1.md` §4 и `01_BUSINESS.md` §9.

## 2. Порядок реализации и зависимости

Волны соответствуют требуемому порядку: **Ф0** окружение/JWT/миграции → **Ф1** первый рабочий вертикальный сценарий → **Ф2** рисковые инварианты → **Ф3** остальные сценарии → **Ф4** отказы и нагрузка. Тесты интеграционных слоёв живут в своих задачах с самого начала (T08), ни одна волна не оставляет их «на потом».

Обоснования нетривиальных зависимостей (остальные — очевидные поставки данных/кода):

- **Архитектурные гейты (T3-03) раньше бизнес-кода.** Иначе нарушения зависимостей врастут до первой проверки, и их исправление станет рефакторингом, а не правилом (T02/L01).
- **Ядро Domain (T3-05) до CRUD и вертикали.** Чистые правила (календарь, аудитория, ранжирование) нужны уже настройке кампании (интервалы челленджа, Q05) и событию; unit-слой снижает риск до входа в интеграционный.
- **Простейшая экономика до составного события (T3-08 → T3-09).** Путь блокировок §3.1 (budgets → wallet_balances) и порядок §3.0 отрабатываются на минимальном агрегате (ручное начисление) до объединения с progress/completions/наградой в одну транзакцию.
- **Траты (T3-12) в волне инвариантов, а не «остальных сценариев».** Трата — носитель E05/E06/SCN-04a; реализация и параллельные тесты сдаются вместе, отдельная волна «сценариев трат» исчезает как класс.
- **Чтения и кеш (T3-10) после вертикали.** Read-модель верифицируется на данных, которые производит вертикаль; кеш-инфраструктура (asOf, miss→PG) переиспользуется затем live-рейтингом (T3-16). Исполнимость Done внутри вертикали обеспечена её собственными минимальными чтениями: PG-чтение live-рейтинга и базовое /me/achievements входят в T3-09 (SCN-01 требует счёт и достижение), полные фильтры/пагинация и Valkey — T3-10/16.
- **Тестовый шов `ITestImpediments` (T3-09).** T08 требует различающих проверок времени, конкуренции и восстановления; шов даёт детерминированные паузы/сбои в оркестрации use case (не в validation/authorization) и переиспользуется в T3-14/16/17/20; в production — no-op. Обоснование абстракции — именно воспроизводимость обязательных проверок (T02).
- **Экспорт (T3-17) после полной книги операций (T3-09/12/13, явно в зависимостях).** Эталонный CSV охватывает все виды движений, включая траты и отмены; снимок зависит от финальной семантики движений (исключение BudgetAllocation и Declined).
- **Изоляционный sweep (T3-18) после T3-16/17** — единый проход по всей поверхности; точечные изоляционные проверки уже встроены в T3-06/10/12 и не отложены.
- **Нагрузка (T3-21) последней:** seed и адаптер маршрутов опираются на весь контракт, а деградационные проходы требуют готового e2e-оборудования (T3-19/20). До Г2 (контракт сверен) адаптер не фиксируется.

E2E и нагрузка — реальное время.

## 5. Definition of Done

Канонические команды (документируются в README, T10; фактические команды и exit codes сдаются):

```bash
python3 auth/jwt.py prepare                # 1) api.env + токены (секрет вне Git) — ДО старта API:
                                           #    env_file auth/.local/api.env создаётся здесь (03_AUTH)
docker compose up -d                       # 2) PG 17, Valkey 9, S3, балансировщик, 2×API, 2×worker
scripts/migrate.sh                         # 3) миграции EF на PostgreSQL 17
scripts/bootstrap.sh                       # 4) компании + активные администраторы (use case)
scripts/test.sh unit|functional|http|persistence|architecture|e2e
scripts/verify-arch-gate.sh                # подсаженное нарушение роняет арх-группу
scripts/load.sh profile                    # k6: основной профиль + деградационные проходы
dotnet format --verify-no-changes
```

Порядок №1→№2 обязателен из чистого клона: compose ссылается на `auth/.local/api.env`, которого нет в Git; без него API не стартует (и это явно диагностируется). Подготовка требует .NET SDK на хосте; повторный `prepare` обновляет токены, сохраняя ключ. Все команды работают из чистого checkout без какой-либо ранее созданной конфигурации (T03/T10).

Гейты (каждый проверяется прогоном, не заявлением):

- **Г1 Среда и миграции.** Чистый клон без локальной JWT-конфигурации: `prepare` → compose healthy (2 API + 2 workers одновременно, T06) → миграции на пустую БД и пошагово M1→M4 зелёные → bootstrap → smoke-запрос с токеном employee123.jwt; отсутствующий `api.env` диагностируется до старта API.
- **Г2 Контракт.** HTTP-группа покрывает все 44 маршрута / 70 метода; статусы/коды/схемы соответствуют `openapi.yaml` 1.2.0 (сверка фактическая); drift только через зарегистрированную поправку (T04).
- **Г3 Тесты.** Все группы зелёные, сырые выводы в артефактах; format и анализаторы без замечаний; арх-гейт с задокументированной мутационной демонстрацией.
- **Г4 Аудит.** Контрольный список B28.3: каждое изменение прав/настроек/бюджета даёт запись с инициатором и временем; `/audit-records` читается с фильтрами и пагинацией.
- **Г5 Восстановление.** PG-отказ → 503/Retry-After/readiness и безопасное восстановление; kill API после commit → идентичный replay; crash worker между upload и Ready → та же попытка; удаление выписки против позднего worker — воскрешения нет; очистка ≤10 мин; финал челленджа ≤5 с.
- **Г6 Нагрузка.** Основной профиль: p95 чтения ≤200 мс / записи ≤500 мс, p99 ≤1 с, корректные ≥99,5 %; потеря/повтор/перерасход = 0 по итоговым бизнес-состояниям; отчёт по всем полям T09; деградационные проходы зафиксированы; выписка 100 000 строк ≤120 с.
- **Г7 Сдача.** README ≤2 стр.; примеры запросов Employee/Admin/Integration; таблица трассировки B/T → реализация/тесты с фактическими именами; commit и пакет артефактов (команды, exit codes, сырые результаты, нагрузочные отчёты, seed и распределение состояний, доля завершений); список ограничений; неисполненное помечено «не проверено» (T10). Обнаруженные дефекты не легализуются правкой требований/тестов.

## 7. Недостатки входа (реальные, отдельно от плана)

1. **S3-образ и версии SDK/пакетов не зафиксированы** (T01; stage-2 §8 явно оставляет этапу 3). Закрывается решением в T3-01 до какого-либо кода; на планирование не влияет.
2. **Обёртка 03_AUTH не проверялась runtime** (в среде подготовки нет .NET SDK — статус в самом документе). Риск перенесён в готовность T3-01 (`jwt.py prepare` на стенде); расхождение поведения `dotnet user-jwts` фиксируется как ограничение, не замалчивается.
3. **Статус stage-2/openapi — `EXTERNALLY_NORMALIZED`, «ожидает независимой проверки G3»** (шапка stage-2), при этом задание этапа 3 объявляет входы утверждёнными. План считает их утверждёнными; если независимая проверка изменит §-ссылки, зависимые задачи перекомпоновываются до их старта.
4. **Нагрузочный стенд** (2×API за балансировщиком с лимитами 1 CPU/1 GiB и т.д.) входом не гарантирован; T09 допускает однократное изменение профиля организатором до зачётных запусков. T3-21 фиксирует фактический стенд в отчёте, замену не выдумывает.
5. **Токены обёртки действуют 1 час**: длительные прогоны (нагрузка, деградация) требуют обновления (`prepare`/`token`); в тестовом коде используются собственные подписанные токены (разрешено 03_AUTH). Учтено в T3-21, на архитектуру не влияет.

Согласование формулировок (не противоречие, изменение входа не требуется): stage-1 SCN-06 говорит об общем «отклонении» трат заблокированного — контракт stage-2 §3.3/H0 разделяет исходы (403 для обращений от имени заблокированного user-инициатора и replay событий; 201 Declined `RecipientNotActive` для новой сервисной траты заблокированному получателю). План следует более позднему уточнению контракта.

Других пробелов, требующих решения до старта Ф0, не выявлено. Реализация не начиналась; runtime-проверки на шаге r2 не выполнялись — проверяется план. Следующее действие — повторный gate; до его прохождения исполнение не начинается.
