# Motiva — общие инженерные условия
Версия 3.0 · Не является готовой архитектурой

## T01. Стек и поставка
.NET 10 / ASP.NET Core; EF Core 10 + Npgsql; PostgreSQL 17; Valkey 9; приватное S3-совместимое хранилище. Не заменять PostgreSQL другой БД, Valkey — памятью, S3 — локальной файловой системой. Локальный S3-сервис выбирает агент; его точный образ фиксируется перед исполнением. Работа с локальным S3 не доказывает совместимость со всеми возможными S3-провайдерами.

Фиксировать SDK, пакеты и образы без плавающего latest; использовать lock-файлы. Версии patch и доступ к документации одинаковы внутри серии. Миграции должны исполняться именно на PostgreSQL 17, включая пустую БД и переход от предыдущей миграции. Не использовать специфические возможности PostgreSQL 18 по умолчанию провайдера [S2].

## T02. Структура, стиль, поддерживаемость
Отдельные проекты Domain, Application, Infrastructure, Api и Worker; названия с префиксом Motiva. Дополнительный Contracts допустим при необходимости. Это минимальные границы, не предписание CQRS/DDD/MediatR/repository. Внутри — группировка по функциональности, а не одна папка со всеми обработчиками.

Domain не зависит от EF/HTTP/SDK; Application — от инфраструктурных реализаций. API и Worker подключают Infrastructure в composition root; endpoint/worker orchestration не работают напрямую с DbContext, Npgsql или S3 SDK. DTO не являются EF entities; IQueryable не выходит за границу хранилища. За каждую дополнительную абстракцию должно быть понятное основание. Архитектурные тесты обеспечивают принятые ограничения, а не только проверяют названия проектов.

Общий стиль: приложенный `.editorconfig`, file-scoped namespaces, явная доступность, PascalCase для типов/методов, camelCase для параметров, `_camelCase` для закрытых полей; nullable включён. Асинхронный ввод-вывод, CancellationToken по цепочке, нет `.Result`/`.Wait()` в обработке запросов. `dotnet format --verify-no-changes` и штатные анализаторы проходят; новые compiler/analyzer warnings не подавляются глобально. Исключения правила локальны и обоснованы. Generated code не оценивается как рукописный.

## T03. Идентичность и разрешения
Только подписанные тестовые JWT по `03_AUTH.md`. Никаких login/registration endpoints, паролей или публичного выпуска токенов. Бизнес-профиль сотрудника, активность, теги, владельцы кампаний и grants интеграций хранятся в приложении; это не identity-система. Проверка их актуальности обязательна. Корпоративная роль Admin задаётся тестовым токеном; смена этой роли требует нового токена, мгновенный отзыв самого JWT вне объёма. Блокировка бизнес-профиля действует немедленно по B05.

Все входные идентификаторы проверяются на принадлежность компании и право действия. Сотрудник определяется из проверенного токена; masterId из запроса не переопределяет его. Сервисный токен не имеет личного кошелька. Только начальное создание компаний и активного администратора допускается доверенным bootstrap через application use cases; остальные данные создаются через штатные административные операции, без ручных INSERT.

## T04. REST и контракт
Спроектировать REST API ресурсов, без глаголов в путях и универсальных `/execute`/`/action`. Минимальные семейства: employees; resources; campaigns со streams/tasks/milestones/challenges; achievements; campaign budgets/allocations; integration grants и purchase systems; progress events; wallets/operations/reversals; leaderboards; audit records; exports/download links. Администрирование тоже доступно через защищённый API, а не только seed/CLI. Полный состав методов и URL проектирует агент на этапе 2.

Каждая комбинация method + route + status + media type имеет одну документированную схему. Роль, пустая коллекция, кеш или готовность отчёта не меняют форму успешного DTO. Операции разных видов допускают общую схему с явно описанными nullable-полями, но не object/dynamic/произвольный JSON. GET не изменяет бизнес-данные. Списки имеют устойчивый порядок, ограниченный размер (по умолчанию 50, максимум 100) и один envelope `items + nextCursor`; живой рейтинг — top N и отдельное собственное место. Пагинация append-only истории не пропускает и не дублирует существовавшие записи при новых вставках.

Создание ресурса — 201 + Location; чтение — 200; удаление — 204; ошибки — Problem Details с постоянным machine-readable `code` и traceId. Неверный/просроченный токен — 401; недостаточные полномочия — 403; чужой/недоступный персональный объект — 404; неверные поля — 400; конфликт повторного номера/состояния — 409. Для PUT/PATCH/DELETE существующих изменяемых настроек нужен If-Match: отсутствующий — 428, устаревший — 412. Экономические операции и удаление выписки не используют эту предварительную версию; их защита описана отдельно. Использовать strong ETag; серверные версии не заменяют защиту бюджета/баланса.

**Экономический отказ** корректно сформированной операции сохраняется как ресурс результата со статусом Declined и возвращается через ту же схему/201, что Posted. Ошибки доступа/валидации ресурса операции не создают. Нельзя считать любой 201 проведённым начислением. Завершение без ресурсной награды также имеет явный результат.

На этапе 2 сдать OpenAPI и таблицу покрытия B01–B37. После утверждения не менять контракт без зарегистрированной поправки. Наличие OpenAPI само по себе не подтверждает соблюдение REST.

## T05. Повторы, числа и время
Бизнес-номера B16/B24 бессрочны; хранятся независимо от кеша. Для остальных создающих POST (настройки, заказы экспорта, ссылки) нужен Idempotency-Key минимум на 24 часа. Scope: company + проверенный initiator + операция/целевой ресурс + key. Перестановка JSON-полей и ресурсных позиций не меняет смысл; изменение существенных данных — 409. Успешный повтор возвращает исходные ID, статус и представление; GET читает актуальное состояние. Текущая авторизация проверяется первой, сохранённый результат — до повторной проверки уже изменившихся бизнес-предусловий. Исключение: удалённый экспорт не выдаёт даже ранее сохранённую download link; 409 после проверки доступа. Ошибки доступа/валидации/временной недоступности не кешировать как успех. Конкурентный повтор может ограниченно ждать либо получить 503/Retry-After; последующий повтор обязан восстановить результат.

masterId — положительный Int32; companyId — UUID. Коды ресурсов/кампаний/стримов/заданий/достижений: ASCII `[A-Za-z0-9_-]{1,40}`, уникальны в соответствующем родителе без учёта регистра; названия 1–200 символов, описания до 2000; теги `[a-z0-9-]{1,32}`. Внешние номера 1–100 ASCII символов, регистрозависимы. Цели, delta, отдельные суммы и очки ≤ 1 000 000 000; баланс и бюджет ≤ 10^15. Только точная целочисленная арифметика с проверкой переполнения; выход за пределы — 400 без частичных эффектов. Внешние даты требуют UTC offset, выход UTC; время тестируется через TimeProvider. Производственное изменение времени через HTTP запрещено.

## T06. Конкуренция и зависимости
Два API-процесса и два workers должны работать одновременно. Защита бюджета, кошелька, повторов, отмен и достижений не может зависеть только от памяти процесса или Valkey-lock. Повтор после commit, потери ответа и рестарта не дублирует эффект. Бизнес-история согласована с изменением данных; access log не заменяет её.

Valkey используется для неперсонального каталога и живого рейтинга: допустимое отставание 30 и 5 секунд соответственно; `asOf` сообщает свежесть. Актуальные права, балансы, экономические решения и ограничения на выполнение не берутся из устаревшего кеша. Просроченное/повреждённое значение — miss. Поздний cache fill не продлевает жизнь старому снимку. При отказе кеша — ограниченное ожидание и чтение из PostgreSQL.

Временный отказ S3 не останавливает основной учёт; задачи экспорта повторяются после восстановления. Недоступность PostgreSQL — ограниченный по времени 503, не ложный успех. Readiness показывает невозможность обслуживать основные операции; liveness не падает лишь из-за недоступности внешней зависимости. Нужны структурированные логи, correlation/trace ID, метрики задержек/ошибок, повторов и состояния очереди; не логировать токены, ключи и signed URLs.

## T07. Экспорт
Формат CSV UTF-8, LF, header: `operationId,masterId,resourceCode,amount,kind,campaignId,originalOperationId,createdAtUtc`. Одна строка на проведённое движение ресурса, amount со знаком. Порядок createdAtUtc, operationId, resourceCode по возрастанию; диапазон времени [from,to). Коды выводятся в нормализованном верхнем регистре, пустые необязательные поля пустые. Поля с CSV-значимыми символами экранируются. Пользовательский свободный текст в этот файл не входит.

Формировать файл потоково, без чтения всей выписки в память API/worker. На исправном стенде поддержать выписку в 100 000 строк за ≤120 секунд. Снимок B36 фиксируется согласованно и сохраняется для повторов; фильтр по timestamp без защиты от позднего commit не заменяет снимок. Worker восстанавливается после crash между созданием файла и Ready. Ready указывает на неизменяемые проверенные байты. S3 приватный; download link отдельным ресурсом, срок ≤60 секунд. Повтор ключа ссылки возвращает ту же, возможно истёкшую ссылку; новая требует нового ключа. Удаление запрещает новые ссылки немедленно; объект и незавершённые загрузки очищаются не позднее 10 минут после восстановления зависимостей. Гонка удаления и worker не воскрешает отчёт. Финальный рейтинг появляется не позднее 5 секунд после завершения при исправных зависимостях и не теряет принятые события.

## T08. Тесты: что обязательно
| Слой проверки | Условия |
|---|---|
| Unit | Чистые правила, границы календаря, точные суммы; doubles допустимы на этом уровне. |
| Functional integration | Реальные PostgreSQL 17, Valkey 9 и S3 для использующих их сценариев. Arrange/Act/Assert через штатные application use cases или HTTP, без DbContext/DbSet/SQL/NpgsqlConnection, включая fixtures и helpers. Не обходить validation/authorization pipeline. |
| HTTP/contract | Реальные подписанные JWT, middleware, сериализация, статусы, ETag и схемы. Test-only authentication handler не заменяет эти проверки. |
| Persistence/migrations | Отдельная группа; прямые EF/SQL допустимы для mappings, constraints и миграций, но не заменяют functional integration. |
| Architecture | Проверка зависимостей и запрещённых обращений. Проверяется, что компилируемое нарушение действительно вызывает падение. |
| End-to-end | Отдельные процессы, конкуренция, рестарт, отказ кеша/S3, экспорт и контроль неизменяемого снимка. |

Инфраструктурное создание/удаление тестовой БД и применение миграций допустимо вне бизнес-Arrange. Заполнение бизнес-таблиц обходным SQL даже через fixture запрещено. Параллельные тесты изолированы, время управляемо, ожидания ограничены и не построены на произвольном Sleep. Ожидаемые значения выводятся из B-правил, а не production-калькулятора/текущего вывода. Зелёный набор и coverage не доказывают правильность ожиданий [S3].

После первой сдачи проверяющие независимо проверят несколько семантических изменений кода, закрепляют ли тесты ошибку. Изменение считается обнаруженным только если правильный вариант проходит, исполняемый ошибочный падает по нужному бизнес-правилу. Агента не просят заранее писать эталонное приложение или отдельный банк дефектов.

## T09. Нагрузка и доступность
Предложенный общий профиль: 10 000 сотрудников основной компании + 100 другой; 3 ресурса; 10 кампаний; 10 заданий в каждой; 100 000 исторических событий и 100 000 движений. Подготовка через валидируемые use cases/batch, вне измерения. Одинаковый seed=42 и распределение состояний; никаких «невозможных» прямых вставок. Для трат заранее достаточно средств, для прогресса новые номера; доля завершений сообщается отдельно.

Два API за одним балансировщиком; по 1 CPU/1 GiB каждому, PostgreSQL 2 CPU/4 GiB, два workers суммарно 1 CPU/1 GiB, Valkey 0.5 CPU/0.5 GiB, S3 1 CPU/1 GiB. Генератор нагрузки отдельно; занятость его ресурсов фиксировать. При недоступности такого стенда организатор меняет профиль один раз для всех **до** зачётных запусков.

Открытая нагрузка: 100 запросов/с, 60 с прогрев + 300 с измерение. Состав: 50% каталог, 25% личный кошелёк, 10% live leaderboard, 10% новые progress events, 5% новые spends по 1 единице. Подготовить адаптер маршрутов по утверждённому OpenAPI; не подменять операции на лёгкие аналоги. Отдельно записать сценарий двух конкурентов за последний остаток. Цели: p95 чтения ≤200 мс, записи ≤500 мс, p99 ≤1 с, доля корректных ответов ≥99.5%; потеря/повтор/перерасход недопустимы. Это условия эксперимента на данном стенде, не обещание промышленного SLA. Максимальный устойчивый RPS можно дополнительно измерить тем же составом на 250/500/1000; результаты не заменяют основной профиль.

В отчёте: planned/sent/completed RPS, goodput (корректные ответы в пределах 1 с), p95/p99 по видам, таймауты, ошибки, dropped iterations, CPU/RAM и задержки БД. Проверять итоговые бизнес-состояния, а не только HTTP-коды. Во время отдельного прохода отключить Valkey на 30 с, S3 на 30 с, один API на 10 с: основной профиль продолжает работу, отмечается фактическая деградация. PostgreSQL выключить отдельно: ожидаем 503 и безопасное восстановление, не засчитываем эти ответы как бизнес-доступность. Правило открытой нагрузки — [S4].

## T10. Сдача и воспроизводимость
Один сценарий запуска из чистого checkout, отдельные команды миграций/bootstrap/тестов/нагрузки; Compose, .env.example без секретов, README до двух страниц. Реальный ключ не коммитить. Добавить запросы примеров Employee/Admin/Integration. В репозитории — актуальные документы этапов и связь требования → реализация/тест. При сдаче: commit, фактические команды/exit codes, исходные результаты тестов, нагрузочные результаты, список ограничений. Неисполненное явно помечать «не проверено». Не переписывать требования и тесты для легализации обнаруженного дефекта.
